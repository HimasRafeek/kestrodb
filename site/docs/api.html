Reference

Node.js API

Database runs the engine inside your Node process through a Node-API addon (bin/kestro.node). Calls are synchronous, like node:sqlite’s DatabaseSync; a write returns only once it is durable on disk.

Opening a database

import {Database} from 'kestrodb';   // or './index.mjs' inside this folder

const db = new Database(path, {create: false, ...options});
// or: const db = Database.open(path, options);

One process owns a database file at a time. Inside that process, reads are fast enough to call synchronously, and async writes are group-committed on a background thread. To share a database between processes, use kestro-server.

Open options

All options are optional.

OptionDefaultMeaning
createfalseCreate a new file. Refuses to overwrite an existing one.
jsonValidation'strict''strict' rejects values that JSON.stringify would silently change (Dates, Maps, getters, sparse arrays, unsafe integers). 'basic' stores what JSON.stringify returns, like most databases’ Node bindings, and writes faster.
verifyOnOpenfalseFinish verifying the whole file before new Database returns, instead of in the background (see index snapshot).
readMode'auto''auto' reads through memory mapping; 'pread' uses file reads.
orderedSyncfalseLinux/macOS: flush data before metadata, then again before returning.
indexMemory32 MBBytes of RAM for the key index before it moves to a memory-mapped <path>.idx file (a cache, rebuilt from the log when missing or damaged); 0 keeps it all in RAM.
orderedMemory16 MBBytes of RAM for ordered keys and secondary indexes (SQL) before their pages move to <path>.sets (deleted on close); 0 keeps them all in RAM.

The cost of 'strict': in-process bulk load measured 302,000 writes/s strict against 519,000/s basic.

SQL

db.sql('INSERT INTO users (email, name, age) VALUES (?, ?, ?)', ['kestro@example.com', 'Kestro', 30]);
// → {changes: 1, lastInsertId: 1}
db.sql('SELECT * FROM users WHERE age >= ? ORDER BY age DESC LIMIT 10', [18]);
// → {rows: [{id: 1, email: ..., name: 'Kestro', age: 30}]}

params is an array for ?, ?N and $N placeholders, or an object for :name and @name (see placeholders). Each statement is atomic and durable before it returns. See the SQL reference.

Query helpers and prepared statements

db.execute('INSERT INTO users (email, name) VALUES (:email, :name)', {email: 'a@example.com', name: 'Ann'});   // → 1 (rows changed)
const user = db.queryOne('SELECT * FROM users WHERE id = ?', [db.lastInsertId]);   // first row or null
const count = db.queryValue('SELECT COUNT(*) FROM users');                           // first column of the first row
const byCity = db.prepare('SELECT * FROM users WHERE city = ?');
const rows = byCity.all(['Kandy']);                                                 // also get, value, run

RemoteDB has the same methods, returning promises; see the common client API.

Transactions

A Database is one connection, so BEGIN ... COMMIT (or ROLLBACK) run through sql(), or db.transaction(fn), group its statements into one atomic, durable commit:

db.transaction(() => {        // COMMIT, or ROLLBACK and rethrow if fn throws; fn may also be async
  db.execute('UPDATE accounts SET balance = balance - ? WHERE id = ?', [amount, from]);
  db.execute('UPDATE accounts SET balance = balance + ? WHERE id = ?', [amount, to]);
});

db.sql('BEGIN');              // the same by hand
db.sql('UPDATE accounts SET balance = balance - ? WHERE id = ?', [amount, from]);
db.sql('SAVEPOINT fee');
db.sql('UPDATE accounts SET balance = balance - 1 WHERE id = ?', [from]);
db.sql('ROLLBACK TO SAVEPOINT fee');   // undo only the fee
db.sql('COMMIT');             // or db.sql('ROLLBACK')
  • Plain BEGIN transactions write one at a time (serializable); other writers wait for one and reads never do. Keep transactions short.
  • BEGIN CONCURRENT transactions run side by side under snapshot isolation: one holds no gate until COMMIT, and the first to commit a row wins. A later one that wrote the same row fails with CONFLICT and is rolled back, so run it again from BEGIN. Foreign keys and unique constraints are checked again at COMMIT. Two such transactions can each read what the other writes and both commit (write skew); use plain BEGIN where that matters.
  • Long reads do not hold up writes: a long query lets waiting commits through and keeps reading the state it started with (MVCC). stats().snapshotYields counts the commits let through and stats().snapshotMemory the memory kept for such reads.
  • Inside a transaction, key/value writes (such as set, delete and batch) on the same Database are refused, because they would wait for the transaction itself. CREATE/DROP must run outside transactions.
  • Closing the database rolls an open transaction back. A transaction can change up to 65,536 rows.

Collections, keys and values

  • Collections are names like users (letters, digits, _, up to 64 characters).
  • Keys are any text up to 512 bytes (valid Unicode, no NUL).
  • Values are JSON, up to 256 KiB each.
db.set('users', 'kestro', {name: 'Kestro'});        // → {version, operations: 1}
db.get('users', 'kestro');                          // → {version, value: {name: 'Kestro'}}
db.getMany('users', ['kestro', 'missing']);         // → [{version, value}, null]
db.delete('users', 'kestro');

Versions and optimistic concurrency

Versions let you update safely: pass {expectedVersion: v} and the write fails with CONFLICT if someone else changed the key since you read version v. 0 means “must not exist yet”.

const before = db.get('items', '0');
db.set('items', '0', {...before.value, count: 1}, {expectedVersion: before.version});  // fails if someone changed it meanwhile
db.set('items', 'new', {count: 0}, {expectedVersion: 0});                               // only if it does not exist yet

Batches

A batch is one all-or-nothing transaction, and every operation in it gets the same version. Operations look like {type: 'set' | 'delete', collection, key, value?, expectedVersion?}. Duplicate keys within one batch are rejected.

db.batch([
  {type: 'set', collection: 'users', key: 'kestro', value: {name: 'Kestro'}},
  {type: 'delete', collection: 'sessions', key: 'old', expectedVersion: 7},
]);   // → {version, operations: 2}

Async writes and group commit

setAsync, deleteAsync and batchAsync queue writes for a background writer thread. Every write queued while a flush is running shares the next flush (group commit), and each promise resolves after the flush that covers it. Async writes issued in the same tick go to the native writer in one call and commit as one group; each still gets its own version, or fails alone. Use them when many writes are in flight at once, such as in a server.

await Promise.all(['a', 'b', 'c'].map(k => db.setAsync('items', k, {k})));   // concurrent writes, one commit

Streaming large imports

bulk.mjs (kestrodb/bulk) streams a large import as a series of batches:

import {Database} from './index.mjs';
import {importBatches} from './bulk.mjs';
const db = new Database('./app.kdb');
try {
  async function* operations() {
    for (let i=0; i<10000; i++)
      yield {type:'set', collection:'items', key:String(i), value:{i}};
  }
  for await (const receipt of importBatches(db, operations(), {batchSize:256}))
    console.log(receipt.committedOperations, receipt.version);
} finally { db.close(); }

Each batch is one atomic transaction and receives one version; the whole stream is not atomic. Earlier yielded receipts remain committed if a later batch fails, and the failed batch can have an unknown outcome after an I/O error. The helper does not retry automatically: reconcile before resuming. It consumes at most one batch of operations before awaiting its commit, and breaking the loop stops further submissions.

Stats, verify, backup and compaction

db.stats();                    // key count, file size, last version, openedFrom, verification, indexMode, ...
db.verify();                   // → {ok: true}, or throws CORRUPT
db.backup('./backup.kdb');     // online, verified copy; refuses to overwrite
db.compact();                  // online: rewrites this file with only current values
db.compactTo('./compact.kdb'); // copy with only current values

For example, the benchmark recorded these stats() fields for a fresh in-process database on Windows (results/bench-history.json): keys, indexMemory, indexFileBytes, orderedMemory, orderedFileBytes, bytes, txid, readMode ("mapped"), commitPolicy, openedFrom ("log-replay"), verification ("at-open"), indexMode ("memory"), pointChecksum, platform, fileSync, namespaceSync and sha256Backend.

Updates and deletes leave old versions in the file. compact() reclaims that space while reads and writes continue: current values go to a new file shard by shard, transactions committed meanwhile are appended, and writes pause only for the last few transactions and the switch. The new file is checked in full before it replaces the old one, and a crash at any point leaves the database whole. It returns the committed bytes before and after. Nothing reclaims space automatically; see online compaction.

Backups, archive and restore

db.archive('/mnt/other-disk/archive');   // appends what was committed since the last call → {txid, end}
Database.restore('/mnt/other-disk/archive/archive.kdb', './restored.kdb', {time: new Date('2026-11-17T14:32:10Z')});
Database.restore('./backup.kdb', './restored.kdb');                      // a whole backup
Database.restore('/mnt/other-disk/archive/archive.kdb', './restored.kdb', {txid: 48211});   // cut after that transaction
  • backup() reads the commit point under a short lock and copies the committed bytes while writes continue; every copy is checked (SHA-256 and the chain of every transaction) before it is published.
  • archive(dir) keeps dir/archive.kdb, a valid database holding every transaction archived so far, and dir/timeline. Each call appends only what was committed since the last one.
  • Database.restore(source, dest, {txid, time}) writes a new database from a database, backup or archive.kdb, cut after transaction txid, or at the last archived point at or before time (a Date or milliseconds). It never overwrites.

kestro-server does the same on a schedule (--backup-every, --archive-every); see Backups and restore.

Errors

Errors from the engine start their message with a code, and native errors thrown to JavaScript carry the code in error.code. Invalid arguments caught in JavaScript throw an error whose code property is INPUT or LIMIT.

CodeMeaning
INPUTInvalid argument, value or SQL.
LIMITA size limit was exceeded (for example a value over 256 KiB of JSON).
CONFLICTA failed expectedVersion, or a duplicate id or unique value in SQL.
LOCKEDAnother process has the file open.
CORRUPTStored data failed its checks. It is never returned, and the engine does not repair it.
UNKNOWN_COMMITAn I/O failure left a write’s outcome unknown: reopen and check before retrying.
UNSUPPORTEDSQL that is not supported yet.
CLOSEDThe database was already closed.
 
try {
  db.set('users', 'kestro', {name: 'Kestro'}, {expectedVersion: 3});
} catch (e) {
  if (e.code === 'CONFLICT') { /* re-read and retry */ }
  else throw e;
}

Other Node.js clients

RemoteDB (server)

remote.mjs (import {RemoteDB} from 'kestrodb/remote') connects to kestro-server so many processes (and languages) share one database. Every call is async and returns the same shapes as Database, including query, execute, transaction and prepare; admin connections also have compact() and promote() (for replication). For a cluster, give every member (an array or a comma-separated string): writes go to the leader, also during an election. See Server & clients.

The worker process (advanced)

worker/client.mjs (import {NativeDB} from 'kestrodb/worker') runs the same engine in a separate process (bin/kestro-worker) and talks to it over a pipe. Every call is async. It is slower (each read is a round trip between processes), and most apps should use Database. Reasons to use it anyway:

  • a crash in native code ends only the worker, not your Node process;
  • your environment cannot load a native addon (kestro.node);
  • you want even disk flushes kept off Node’s process entirely.
import {NativeDB} from 'kestrodb/worker';

const db = await NativeDB.open('./app.kdb', {create: true});
await db.set('users', 'kestro', {name: 'Kestro'});
console.log(await db.get('users', 'kestro'));
await db.close();

It accepts the same options. Requests issued together travel in one pipe write, and consecutive writes are group-committed. The test suite also uses the worker to inject crashes at exact points of a commit.
