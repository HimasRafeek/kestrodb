Engine

Durability & integrity

Every write is on disk before the call returns, every transaction is hash-chained, and every value is checked when read. This page explains what that means on each platform, what the file looks like, and what has and has not been tested.

Durable commits

A durable commit means:

PlatformHow a commit becomes durable
WindowsThe database handle is opened write-through (FILE_FLAG_WRITE_THROUGH), so each write completes only after it reaches stable media. Commits overwrite preallocated space, and the engine calls FlushFileBuffers whenever it grows that space, so the file’s size is durable before any commit relies on it.
Linuxfdatasync before each acknowledgement (data, plus the file size when it changes; commits overwrite preallocated space).
macOSF_FULLFSYNC.

Write-through on Windows was chosen from a measurement, not assumed: FlushFileBuffers after each small commit cost 333–390 µs; write-through writes into preallocated space cost 67 µs, about 5× less. Write-through on a growing file cost 148–166 µs, because the file size changes on every write — hence the preallocated reserve.

Ordered sync (Linux and macOS)

On Linux and macOS the default omits an optional first barrier; a successful file flush is still required before every acknowledgement. In that single-barrier mode a new metadata slot can reach disk ahead of its data if an unacknowledged write is interrupted; reopen rejects that state. Set orderedSync: true for the original data-before-metadata policy. Both modes reject torn metadata.

Requirements

Use a local file system with working locks and flushes: NTFS on Windows, local POSIX file systems elsewhere. Network shares, cloud-sync folders and multi-host shared disks are not supported.

Storage hardware must honor flush requests (write-through relies on forced-unit-access, as SQL Server does). Power loss is tested in simulation (see below); no physical power-loss testing on real hardware has been performed.

An I/O failure can leave a write’s outcome unknown (UNKNOWN_COMMIT): reopen and check before retrying.

Integrity checks

  • Every transaction is stored with a SHA-256 hash chained to the previous one, and the metadata slots carry their own SHA-256.
  • Every value is checked against a keyed checksum when read: SipHash-2-4 for values up to 2 KiB and keyed BLAKE3 above. These checksums live only in RAM and are rebuilt on open (or taken from the index snapshot).
  • Damaged data is reported as CORRUPT and never returned. The engine does not repair it, so keep backups.
  • verify() re-checks the whole file against its checksums at any time.

File format

The native format is unchanged since 0.6, apart from its markers: new files are written with KDBNAT02 and KDBG0002. Files written by versions before 0.9 use HDBNAT02/HDBG0002; they still open and take new commits, and one file may then hold both spellings. Their index snapshot and .idx cache are rebuilt once. All integers are little-endian; strings and values are length-delimited bytes (UTF-8 JSON from Node). The full byte layout is in FORMAT.md.

Metadata slots

The first 8,192 bytes hold two 4,096-byte slots. Generation G is stored in slot G modulo 2, so a commit always writes the slot that is not current. Each populated slot holds:

248Exclusive committed byte boundary

4832Last group SHA-256
8032SHA-256 over bytes 0–79 (0.9): a slot torn at a sector boundary keeps its fields
1123,952Zero padding
4,06432SHA-256 over the preceding 4,064 bytes

Transaction groups

After the slots comes a log of transaction groups. Each group has a KDBG0002 magic, payload length, transaction ID, flags, operation count and the previous group’s SHA-256, then its operations, then a SHA-256 of header and payload. Each operation holds its kind (set or delete), expected version, key length, value length, key and value. Normal transaction payloads are bounded to 64 MiB.

How a commit is published

  1. Under the writer mutex, validate all expected versions and encode the group. With group commit, several queued transactions are each validated against the ones accepted before them and encoded as their own chained group; one that fails validation fails alone.
  2. Make sure the zero-filled reserve covers the new groups, then write them contiguously (flushing now if ordered sync is on).
  3. Write the next metadata slot and flush the file, covering every write.
  4. Update the in-memory index and return success to every transaction in the commit.

The reserve keeps the file longer than the committed boundary, grown in steps of 1/8 of the committed size (1 MiB to 64 MiB), so commits overwrite allocated bytes instead of growing the file. Bytes past the committed boundary are an uncommitted tail that every reader validates around and removes on open; since 0.8 a clean close also trims the reserve.

On Windows a commit needs one disk write: a group that is complete on disk and continues the chain (next transaction ID, previous hash, SHA-256) is committed, and the metadata slot is written through the cache and reaches the disk lazily (flushed on close). Opening walks past a stale slot and tolerates one damaged slot.

Read consistency

getMany returns one consistent set, including missing keys, and a SQL SELECT sees one committed state. A long SQL read does not hold up writes: it lets waiting commits through and keeps reading the state it started with (MVCC; see SQL consistency). In the key/value API there is no multi-call snapshot: separate get calls may observe different commits.

A SQL transaction (BEGIN ... COMMIT) commits all its statements as one atomic, durable commit; other connections see nothing until COMMIT, then all of it at once. Plain BEGIN transactions write one at a time (serializable); BEGIN CONCURRENT ones run side by side under snapshot isolation, and the first to commit a row wins. A connection that closes or drops rolls its open transaction back, and a failed COMMIT (for example a disk error) ends the transaction. See SQL transactions.

Index snapshot

On a clean close, and in the background once commits have been quiet for 50 ms, KestroDB writes an index snapshot into the end of the file: every key with its location, version and checksum, as one hash table per shard. The next open uses it directly instead of re-reading the whole log.

  • Compatible. It sits after the last committed byte, which every version since 0.4 treats as leftover space and discards. Older versions just re-read the log; so does 0.9 when the snapshot is missing, stale, damaged or from another file.
  • Lazy. Lookups read the snapshot’s tables straight from the mapped file. Each of its 64 sections is checksummed the first time it is used; a damaged one makes KestroDB rebuild the index from the log and carry on. The first write builds the in-memory index; read-only sessions never pay for it.
  • Verified in the background. Once the database has been open for 50 ms, a background thread performs the same checks a full re-read would (every transaction’s SHA-256, the hash chain, every value’s checksum). If it finds damage, every later operation fails with CORRUPT. A database closed within 50 ms skips this; reads still check every value they return. With verifyOnOpen: true the full check finishes before open returns, so a damaged file fails to open. stats() reports openedFrom, verification and indexMode.
  • Crash-friendly. Snapshots are also written when writes go quiet, so the first open after a crash is still fast, provided nothing was committed after the last snapshot.
  • Checksum key. Value checksums are keyed. After a snapshot open, the key is the one stored in the snapshot: checksums still detect damaged bytes, but no longer stop someone who can rewrite the file (the same level as the file’s SHA-256 chain).

Backups and compaction

  • Online backups. The log is append-only, so backup(path) reads the commit point under a short lock and copies the committed bytes while writes continue. Every copy is checked (SHA-256 and the chain of every transaction) in bounded memory before it is published under its final name.
  • Scheduled backups and continuous archive. kestro-server can write a backup on an interval and keep the newest N, and keep an incremental archive (archive.kdb + timeline) for point-in-time restore by transaction or time into a new file. See Backups and restore.
  • Online compaction. compact() rewrites the file to hold only current values while reads and writes continue. The new file is replayed in full before it replaces the old one (POSIX: an atomic replace; Windows: two renames, recovered on open), so a crash at any point leaves the database whole. See online compaction.
  • compactTo(path) writes a copy with only the current values. Old versions stay in the file until you compact; nothing reclaims space automatically. The compacted file keeps each key’s version, so expectedVersion checks keep working.
  • Copies use a temporary file on the destination file system, flush and validate it, then publish it without overwriting. None silently replaces an existing database.
  • A large compacted file (a checkpoint above 64 MiB) and its backups require a 0.6 or newer reader.
  • The .idx sidecar and the .sets scratch file are caches: copy only the .kdb file for backups.

Moving a database between systems

The file format uses explicit little-endian integers and no pointers or OS-specific layout. Close the database or use backup(), copy the file, open it and call verify(). Copying a closed file copies its index snapshot too; backup() and compactTo() copy committed data only, and the copy writes a snapshot when it is next closed.

If a server’s database file is replaced (a restored backup), in-process readers report STALE; restart the workers. To keep a live copy on another machine, run a follower.
