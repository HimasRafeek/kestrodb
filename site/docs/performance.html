Performance

All published benchmark results, with the machine, the settings and the places where KestroDB does not lead. Higher is better in every table. The raw data lives in the project’s results/ folder, and the benchmark tracker charts the leaderboard and the progress across versions.

Read these numbers with their context. The key/value and SQL tables come from one machine (Intel i5-14400) on 2026-11-20: Windows 10, and Ubuntu 24.04 under WSL2 on the same machine. Older tables carry their own dates; some come from a shared Linux VPS. Durability is matched: every engine acknowledges a write only after asking the OS to make it durable. Run the benchmarks on your own hardware before relying on them.

KestroDB’s figures are its in-process addon. The read rows have the smallest margins (1.05–1.18× on Linux, 1.19–1.27× on Windows); run the benchmark on your own hardware before relying on them.

Engine order. The engines alternate inside each phase and their order rotates with every phase and run: an engine that runs right after another’s background work (LevelDB compacts on its own threads) pays for it, and with a fixed order that was always KestroDB (on Linux its mixed row measured 248K against LMDB’s 451K that way; 574K against 361K with the rotation, 523K against 405K in the latest run). Point reads one at a time take about 22 ms per engine, so they move the most with machine load: an earlier full run had LMDB 3% ahead there (743,400 against 722,100/s). Since then a point read’s integrity check costs about 30 ns less (the checksum loads its input a word at a time and computes only the half it compares), and KestroDB leads that row 1.20×.

MVCC costs nothing measurable: the 0.9.0 build before it and this one, alternated on the same machine (five rounds each), are within a few percent on every key/value row, the new build ahead on most; point SELECTs became 60–75% faster with their direct path.

Since 0.8.0 (2026-11-15). Durable writes got about twice as fast (one at a time: 10.5K/s in 0.8.0, 18–24K/s across runs now; Windows flush timing moves this row the most). The open row (31.7M → 21.0M keys/s) measures close + open + one read, ten times: since commits write only their group (the commit slot is written without waiting), the first close after writes flushes the slot once (about 1 ms on Windows); a reopen without writes in between takes about 0.67 ms (30M keys/s). Opening no longer lists the database’s directory (1.55 ms → 0.70 ms with 2,000 other files). The rows move by 10–15% between single runs on this machine when other programs run (the mixed row measured 493K–578K on 2026-11-20), so changes are judged with the builds alternated.

Median of 5 runs (node bench/sql-compare.mjs --runs 5). KestroDB is first in all eight on both. Aggregates that cannot use an index read an in-memory column cache. Row-returning scans. The full-scan rows above are aggregates, which read the in-memory column cache. A SELECT that returns whole rows from a full scan without an index (no aggregate) still reads and parses every row, because rows are checksum-verified JSON documents. Index the columns you filter on.

PHP and Python: many processes

Windows 10, i5-14400 (10 cores, 16 threads), 2026-11-15. N processes at once, as PHP-FPM or gunicorn workers would run. 300 durable single writes and 20,000 random point reads per process, ~230-byte JSON documents, 20,000 keys. KestroDB writes through kestro-server and reads in-process (readFrom / read_from).

Durability is matched: KestroDB replies after its flush; SQLite (PDO / sqlite3) runs WAL with synchronous=FULL; MySQL 8.0 runs InnoDB with innodb_flush_log_at_trx_commit=1 (binary log off, which favours MySQL). Every engine stores JSON text and decodes it on read.

Server capacity

Measured with node bench/stress.mjs (Windows, i5-14400): every connection sends one request at a time like a PHP worker, 90% point reads and 10% durable writes, 100,000 keys.

ConnectionsOperations/sDurable writes/sp99 latencyErrorsServer memory
100206,71020,3401.1 ms027 MB
1,000176,99517,6229.1 ms055 MB
2,000174,57817,54716.7 ms094 MB
4,000168,78616,96534.6 ms0172 MB
  • Throughput holds as connections grow; latency grows with the queue (requests wait their turn).
  • Each connection costs about 40 KB plus a thread; the default limit is --max-connections 1024.
  • Key index memory. The key index uses at most about 32 MB of RAM by default (indexMemory in Node, --index-memory MB for kestro-server; 0 keeps it all in RAM). Past that it moves to a memory-mapped file next to the database (<file>.idx), and RAM keeps only recent changes: 5,000,000 keys used 53 MB in kestro-server (was 327 MB), and 2,000,000 keys need about 16 MB of index RAM with random reads as fast as before (about 1.7 million per second in-process). The index file is a cache: if it is missing, stale or damaged, it is rebuilt from the database log.
  • Ordered keys and secondary indexes (used by SQL ORDER BY, ranges and indexed WHERE) have their own budget, 16 MB by default (orderedMemory in Node, --ordered-memory MB for kestro-server): past it their least recently changed pages move to a scratch file (<file>.sets, deleted on close), and they are built with an external sort. A 1,000,000-row table with two indexes needs about 10 MB for them instead of 118 MB, at the same or better speed.
  • Copy only the .kdb file for backups; stats() reports indexMode, indexMemory, indexFileBytes, orderedMemory and orderedFileBytes. The 1 GB server scenario has not been measured yet.

Server capacity on Linux

On the same shared 2-vCPU VPS, bench/stress.mjs ran 100, 500 and 1,000 connections with no errors, at about 22,000 operations/s; 1,000 connections used 46 MB. Before the paged key index, 1,000,000 keys used 121 MB (126 bytes/key); with it (2026-11-16), 2,000,000 keys used 50 MB instead of 130 MB, and 5,000,000 keys 54 MB.

Caveats

  • The key/value and SQL results come from one machine (Intel i5-14400) on 2026-11-20: Windows 10, and Ubuntu 24.04 under WSL2, whose virtual disk makes every flush slow. The server, PHP, Python and capacity results are from Windows; the older Linux tables come from one shared 2-vCPU VPS. Run the benchmarks on your own hardware before relying on them.
  • Single runs move by 10–15% on this machine when other programs run, more than some read margins (1.05–1.18× on Linux). Durable writes one at a time vary the most on Windows (18–24K/s across runs, disk flush timing); multi-process write numbers vary ±20% between runs.
  • Against PostgreSQL, single-connection durable INSERTs lead by only 1.05×.
  • A SELECT that returns whole rows from a full scan without an index still reads and parses every row (see SQL); SQLite’s numbers in the SQL comparison moved by about 10% between runs.
  • Reads through the server socket are slower than in-process SQLite; the fast read numbers need the client on the server’s machine.
  • Linux ARM64 is tested on GitHub’s runner on every push but has not been benchmarked; macOS is no longer run.
  • Batching (bulk.mjs) amortizes commit and IPC overhead; it does not establish superiority over another database.

Reproduce

cd bench/competitors && npm install && cd ../..
node bench/compare.mjs --runs 5
node bench/compare.mjs --runs 5 --record "what changed"   # adds a run to the tracker

node bench/sql-compare.mjs --runs 5                       # SQL vs SQLite
node bench/server-sql-compare.mjs                         # kestro-server vs MySQL/MariaDB (needs mysql2)
KESTRO_PG_URL=postgres://... node bench/server-sql-compare.mjs   # vs PostgreSQL
node bench/stress.mjs                                     # server capacity
node bench/lang-compare.mjs --lang php                    # add --mysql "mysql:host=...;dbname=bench"
node bench/lang-compare.mjs --lang python

The other databases live in bench/competitors with their own package.json, so KestroDB itself has no npm dependencies. node scripts/lang-results.mjs refreshes the PHP and Python section of the benchmark tracker.
