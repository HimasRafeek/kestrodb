Roadmap

What KestroDB 0.9.0 added, what it does not do today and what is still unvalidated, taken from the project’s changelog, README, SQL reference and to-do list. The sources do not announce dates, so nothing on this page is promised.

Added in 0.9.0

0.9.0 (2026-11-19) follows 0.8.0 (2026-11-15), which added kestro-server, the PHP, Python and Node clients, the C library with reader and owner modes, the in-process Node addon, group commit and the index snapshot. The 0.9.0 entries in CHANGELOG.md:

Enforced constraints Available

CHECK, FOREIGN KEY with NO ACTION, RESTRICT, CASCADE, SET NULL and SET DEFAULT (chained, self-references), and multi-column UNIQUE; ALTER TABLE ADD/DROP CONSTRAINT. Constraints.

More SQL Available

Window functions, CASE, UNION / INTERSECT / EXCEPT [ALL], RIGHT and FULL joins, JOIN ... USING, correlated subqueries, SAVEPOINT / ROLLBACK TO / RELEASE, ALTER TABLE ... RENAME TO, and named (:name, @name) and numbered ($1, ?1) parameters. An aliased table is now known only by its alias. SQL reference.

Replication Available

Followers (--replica-of) seed from the leader, then stream its log byte for byte; they serve reads and refuse writes with READONLY until promote(). Lag in stats().replica. Replication.

Synchronous replication Available

--sync-replicas N: a write is answered once N followers have it durably (RPO 0). --sync-timeout (5 s) before the leader goes on alone (degraded, in stats().sync, until a follower catches up); --sync-strict to wait instead. Synchronous replication.

Automatic failover Available

--cluster, --cluster-self, --cluster-token-file, --election-timeout: the members elect a leader (terms, pre-vote, leader lease); writes are answered once a majority has them; a former leader cuts back writes no majority confirmed and follows. The Node, PHP and Python clients follow the leader. Cluster.

MVCC and BEGIN CONCURRENT Available

Long SQL reads let waiting commits through and keep reading their snapshot. BEGIN CONCURRENT transactions run side by side under snapshot isolation (first committer wins, CONFLICT then retry). SELECT by id or a UNIQUE column reads its row directly. SQL transactions.

Hardening Available

A security review of the server (14 findings, all fixed), statement, transaction and login time limits, simulated power-loss tests, libFuzzer targets, random SQL compared with SQLite, process-kill tests, a soak test, and CI with sanitizers and fuzzing on Linux x64, Linux ARM64 and Windows on every push and pull request (macOS passed through 2026-11-19 and is no longer run). What the tests cover.

Backups and point-in-time restore Available

Online, verified backups while writes continue; scheduled backups with retention; a continuous, incremental archive; restore by transaction or time into a new file (kestro-server --restore, Node, PHP, Python and C). Backups and restore.

Online compaction Available

compact() reclaims the space of old versions while reads and writes continue, and replays the new file in full before it replaces the old one. Online compaction.

Client APIs Available

Query helpers, transactions, prepared statements, error classes per code and reconnect in Node, PHP and Python; PHP persistent connections for PHP-FPM and KestroDB\Embedded; Python DB-API 2.0. Common API.

Java, .NET, Rust and Go clients Available

Java 17+: KestroClient and a minimal JDBC driver, no dependencies.
.NET 8+: an async and blocking KestroClient and a minimal ADO.NET provider, no dependencies.
Rust: the kestrodb crate, with TLS as an optional feature.
Go 1.21+: a Client and a database/sql driver, standard library only.
All four talk to kestro-server; with Node, PHP and Python, clients in seven languages are tested against it. Clients.

Less memory Available

A compact key index that pages to a memory-mapped .idx file past indexMemory (5,000,000 keys: 327 MB → 53 MB in the server), and paged ordered keys and secondary indexes past orderedMemory (1,000,000 rows with two indexes: 118 MB → 10 MB). Server capacity.

The same release also lists faster commits (one disk write per commit on Windows, SQL group commit across server connections) and the SQL base it builds on: enforced column types, transactions, joins and subqueries, ALTER TABLE ... ADD / DROP / RENAME COLUMN and the column cache. See kestro-server against MariaDB and PostgreSQL.

Not supported today

SQL

From the SQL reference’s “Not supported yet” list:

  • WITH before INSERT, UPDATE or DELETE (it works for SELECT)
  • ALTER COLUMN ... TYPE ... USING, MySQL CHANGE COLUMN, several changes in one ALTER TABLE
  • Window EXCLUDE clauses
  • Deferred constraints (checks are never deferred to COMMIT)
  • NATURAL joins
  • MATCH inside joins, stemming and stop words in full-text search
  • LISTEN over tls://, and notifications from other processes
  • SQL through in-process readers: readFrom / read_from answer get/getMany, and SQL from those clients runs on the server

Engine and deployment

From the README’s “What KestroDB does not do” list and ROADMAP.md:

  • Clusters across regions: a cluster answers a write once a majority has it, so members far apart add their round trip to every write.
  • A column cache for row-returning scans: aggregates over a whole table use an in-memory column cache and beat SQLite, but a SELECT that returns whole rows without an index reads and parses every row.
  • Several writing processes on one file: one process owns the file (a second owner gets LOCKED); other processes write through kestro-server and can read the file directly.
  • Read-then-write transactions in the key/value API: there, batches are atomic writes and expectedVersion gives optimistic concurrency; use SQL BEGIN ... COMMIT for transactions that read and then write.
  • Automatic space reclamation: old versions stay in the file until you run compact() (online) or compactTo().
  • One memory budget: the key index and the ordered indexes have their own budgets, but the column cache has a fixed cell cap rather than a RAM budget with eviction, and there is no single setting for the total.
  • Native extensions for each language: PHP and Python use FFI/ctypes over the C library; the Java, .NET, Rust and Go clients talk to the server only, and embedded use from other languages needs a small binding over src/kestrodb.h.
  • Remote reads without a round trip: in-process reads need the database file on the same machine, the server’s or a follower’s.
  • Years of production use: it is fuzzed, power-loss tested in simulation, run under the address and thread sanitizers and soak-tested in CI and on Windows, but it has not yet run real production workloads for long.

Also open in ROADMAP.md: publishing the packages (npm, PyPI, Packagist, Docker Hub), per-platform npm packages, macOS and musl builds and a native Windows service; Laravel, Django and WordPress drivers; change notifications across processes; an event-driven server for tens of thousands of connections (today one thread per connection); certificate revocation, and client certificates in the Go, Rust, Java and .NET clients; HTTPS for the metrics endpoint; faster row-returning full scans; and rate limiting per user.

Also from the README: network shares, cloud-sync folders and multi-host shared disks are not supported. Native TLS on the Windows server (Schannel) was added on 2026-11-20, so a TLS proxy is no longer needed there.
