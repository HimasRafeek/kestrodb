Reference

Server & clients

kestro-server owns one database file and serves it to many clients at once over TCP or a Unix socket, the way MySQL or PostgreSQL would. Apps write through it, and on the same machine they read the file directly in their own process through the KestroDB C library.

Running kestro-server

openssl rand -hex 24 > token.txt   # a long random token
kestro-server --db /var/lib/app/app.kdb --create --tcp 127.0.0.1:7820 --token-file token.txt

It prints KESTRODB READY ... when listening and stops cleanly (writing its index snapshot) on Ctrl+C or SIGTERM.

Group commit across connections

Writes from all connections that arrive together share one disk flush, so throughput grows with the number of clients. Each write is still durable before its reply. Each connection costs about 40 KB plus a thread. At 4,000 connections the server sustained 168,786 operations/s with 0 errors in the capacity test.

Security

The server authenticates every connection, checks every request against the user’s role and tables, and can encrypt TCP connections with TLS. Refused requests fail with errors that start with AUTH.

Users and roles

--users FILE lists one user per line: name role token [tables=a,b].

# name     role       token (or sha256:HEX)                         [tables=...]

RoleMay

adminalso CREATE/DROP/ALTER, verify, backup, compactTo, compact, promote
replicaonly replicate (the user a follower connects as)
  • Tables. A user with tables= may only use those tables (key/value collections count as tables). Every table a SQL statement touches is checked: joins, subqueries anywhere (ORDER BY, LIMIT, HAVING, ...), UNION/INTERSECT/EXCEPT parts, and the tables a write reaches through foreign keys. SHOW TABLES lists only its tables. tables= cannot limit an admin or replica. Only an admin may change rows of a SQL table with key/value writes; other users use SQL, where the table’s constraints apply.
  • Hashed tokens. Store sha256: hashes rather than tokens: echo TOKEN | kestro-server --hash-token prints one. Tokens are compared as SHA-256 in constant time across all users.
  • Token rules. Tokens must be at least 16 characters; a wrong token is refused after a short delay.
  • Single token. A single --token-file (or KESTRODB_TOKEN) still works and makes that token an admin.
  • No users. Without --users/--token-file the server listens only on loopback addresses unless --no-auth says otherwise.
  • Request limits. Ten failed logins from one address within a minute block logins from it for a minute. A reply or result over 64 MB fails with LIMIT (ask for fewer rows), and a transaction may change at most 1 GB (savepoints count their copies).
  • Backup paths. backup(name) and compactTo(name) from a client write the plain file name name into the server’s --backup-dir, and are refused without one.
  • Reserved keys and backup, verify and compaction need admin. stats() reports the connection’s tls, user and role.

TLS

kestro-server --db /var/lib/app/app.kdb --tcp 127.0.0.1:7820 --users users.txt --tls-cert cert.pem --tls-key key.pem

--tls-cert cert.pem --tls-key key.pem makes every --tcp listener TLS-only (TLS 1.2 or newer, with a 10-second handshake limit); Unix sockets stay plain. Clients connect to tls://host:port and verify the server certificate, against the system CAs by default or a CA file you give:

import {RemoteDB} from './remote.mjs';
const db = await RemoteDB.connect('tls://db.example.com:7820', {token, tls: {caFile: '/etc/kestrodb/ca.pem'}});
$db = new KestroDB\Client('tls://db.example.com:7820', getenv('KESTRODB_TOKEN'), 5.0,
                          ['tls' => ['cafile' => '/etc/kestrodb/ca.pem']]);
db = kestrodb.connect("tls://db.example.com:7820", token=TOKEN, tls={"cafile": "/etc/kestrodb/ca.pem"})

Turning verification off is for testing only: Node {tls: {rejectUnauthorized: false}}, Python tls={"verify": False}.

Windows. Linux and macOS builds use OpenSSL; Windows builds use the system’s Schannel (no extra software). On Windows the certificate file may hold the chain (server certificate first) and the key may be PKCS#8, RSA or EC, unencrypted; or give --tls-pfx server.pfx [--tls-pfx-password-file pw.txt] instead. The server keeps its key in the Windows key store (non-exportable, under the account running the server) while it runs and deletes it when it stops.

In-process readers. readFrom and read_from read the database file directly, so file permissions, not the users file, control them.

Tested on Linux with a self-signed certificate and a users file: an admin PHP 8.3 client created a table over tls:// and refused a certificate from another CA, a readonly Python client limited to that table was refused an INSERT with AUTH, and a plain TCP connection to the TLS port failed. On Windows, tests/tls-windows runs the Node, PHP and Python clients, replication and a 3-member cluster over TLS.

Protocol overview

Clients exchange length-prefixed binary frames with the server. Requests can be pipelined; replies come back in order.

  • A frame is a u32 little-endian length, then that many bytes: a one-byte command followed by its payload. Clients cap frames at 64 MiB.
  • A reply whose first byte is 0xFF is an error; the rest is the message, starting with an error code (INPUT, LIMIT, CONFLICT, CORRUPT, AUTH, BUSY, ...).
  • Keys on the wire are collection + "\0" + key, the same keys every client and the C library use, so they all share one database.

The batch payload is the encoding described in src/kestrodb.h: u32 count, then per operation u8 kind (1 set, 0 delete), u64 expected version (all 0xff = any), u32 key length, u32 value length, key, value.

If a connection drops before a write’s reply arrives, that write has an unknown outcome. Clients raise an IO error that says so; check the key before retrying.

Connections

  • Reconnect. A connection the server closed while it was idle (restart, network) is reopened before the next request. Never inside a transaction: the next call then fails with IO ... connection lost inside a transaction; it was rolled back, and the one after reconnects. A request that was already sent when the connection broke fails with IO (for a write: unknown outcome). Turn it off with reconnect: false / 'reconnect' => false.
  • Clusters. Give every member’s address (Node: an array or a comma-separated string; PHP: comma-separated; Python: a list or comma-separated). Writes go to the leader: a READONLY reply from a follower names it, and the client moves there and sends the request again (nothing was applied), also during an election, for up to failoverTimeout (Node, ms, and PHP, seconds; 15 s) or failover_timeout (Python, 15 s). Not inside a transaction: its connection went with its leader. UNAVAILABLE means a majority did not confirm a write in time: its outcome is unknown, as with IO. db.address (PHP $db->address()) is the member in use. See Cluster: automatic failover.
  • PHP-FPM. ['persistent' => true] keeps the connection open across requests in each worker. A transaction left open by a request that died is rolled back when the connection is reused.
  • Threads. One connection per thread (Python threadsafety = 1). Node’s RemoteDB pipelines concurrent calls on one connection.

Transactions per connection

SQL transactions belong to a connection: each RemoteDB, PHP Client, Python client or C library handle runs its own BEGIN ... COMMIT (or ROLLBACK), through sql(), the transaction(fn) helpers, PHP beginTransaction()/commit()/rollBack() or Python begin()/commit()/rollback().

$db->sql('BEGIN');
$db->sql('UPDATE accounts SET balance = balance - ? WHERE id = ?', [$amount, $from]);
$db->sql('UPDATE accounts SET balance = balance + ? WHERE id = ?', [$amount, $to]);
$db->sql('COMMIT');   // or ROLLBACK
  • Other connections see nothing until COMMIT, then all of it at once.
  • Plain BEGIN transactions write one at a time across all connections (serializable): from BEGIN to COMMIT one holds the write gate, so other connections’ writes wait and reads never do. Keep transactions short. Read-only users and followers may not BEGIN.
  • BEGIN CONCURRENT transactions run side by side under snapshot isolation and hold no gate until COMMIT. The first to commit a row wins; a later one that wrote the same row fails with CONFLICT and is rolled back, so run it again. Constraints are checked again at COMMIT. Write skew is possible: use plain BEGIN where that matters.
  • Long reads do not hold up writes: a long query lets waiting commits through and keeps reading the state it started with (MVCC; stats().snapshotYields, stats().snapshotMemory).
  • A server connection that drops rolls its open transaction back.
  • Inside a transaction, key/value writes on the same connection are refused. In-process readers (readFrom, read_from) do not run SQL; it goes to the server.

See SQL transactions for the full rules.

require 'clients/php/KestroDB.php';
$db = new KestroDB\Client('tcp://127.0.0.1:7820', getenv('KESTRODB_TOKEN'), 5.0,

$db->getMany('users', ['kestro', 'missing']);             // one snapshot, in order; null where missing

$st->execute(['city' => 'Kandy']);

    /* someone changed it ($e->kind === 'CONFLICT') */
}
  • new KestroDB\Client($address, $token = null, $timeout = 5.0, $options = []); addresses are tcp://host:port, tls://host:port or unix:///path, or a comma-separated list of a cluster’s members. Options: readFrom, library, tls (PHP SSL context options), persistent and reconnect.
  • set, delete and batch return the new version (an int); get returns ['version' => ..., 'value' => ...] or null.
  • Also stats(), verify(), backup($path), compactTo($path) (plain file names in the server’s --backup-dir), compact() and promote() (admin) and close().
  • One connection per Client. PHP-FPM workers each open their own; the server handles many at once and group-commits their writes. Values are stored as JSON.
  • Errors are subclasses of KestroDB\Exception (see Errors) with a kind property: the leading code (INPUT, LIMIT, CONFLICT, CORRUPT, AUTH, BUSY, ...).

Every call is async and returns the same shapes as Database. Calls made in the same tick travel in one write, and the server group-commits concurrent writes. connect takes one address, or a cluster’s members as an array or a comma-separated string, and also accepts jsonValidation, timeout (default 5000 ms), reconnect, failoverTimeout (ms, default 15 s) and tls (ca or caFile) for tls:// addresses. Errors carry their code in err.code; a transaction lost with its connection is reported, never silently continued outside it. Admin calls include compact() and promote().

In-process reads beside the server

readFrom (PHP), read_from (Python) and KESTRO_OPEN_READER (C API) open the database file without taking ownership; any number of processes can do it while the server writes.

  • Before every read the reader looks at the file’s commit slot (a few memory loads) and, if it moved, checks and applies only the new transactions, so a read always sees every write acknowledged before it, with no network round trip.
  • Values are checksum-verified as in every other mode.
  • The C library stays loaded for the life of the process and keeps readers open, so a PHP-FPM worker pays the open cost once, not per request.
  • Writes keep going through the server, which is then connected only when first needed.
  • Readers answer get/getMany; SQL from those clients runs on the server.
  • If the database file is replaced (a restored backup), readers report STALE; restart the workers. After an online compaction they see STALE and reopen.
  • Readers also work on a follower’s machine, against the follower’s file.

Setup. PHP needs the FFI extension (on by default for the CLI; set ffi.enable=true for PHP-FPM). Both clients find the library through a library option, the KESTRODB_LIBRARY environment variable, or ../../bin relative to the client file. In-process reads need the database file on the same machine as the server (or as a follower).

Why it matters: reading through the server (one loopback round trip per read) measured 38,000/s with 1 PHP process, against 351,000/s in-process. See the PHP and Python benchmark.

Backups and restore

KestroDB’s log is append-only: committed bytes never change. Backups are therefore online: the commit point is read under a short lock and the committed bytes are copied while writes continue. Every copy is checked (SHA-256 and the chain of every transaction) before it is published under its final name, in bounded memory.

  • Scheduled backups: --backup-dir DIR --backup-every 1h --backup-keep 7 writes DIR/<name>-YYYYMMDD-HHMMSS.kdb (UTC) on that interval and keeps the newest N. A backup is a normal database file: open it, copy it elsewhere, or restore from it.
  • Continuous archive (point-in-time recovery): --archive-dir DIR --archive-every 1s keeps DIR/archive.kdb, a valid database holding every committed transaction archived so far, and DIR/timeline (unix_ms txid end per step). Each step appends only what was committed since the last one, so it costs what was written, not the database size; the server takes a last step when it stops. Put the directory on another disk or sync it to another machine (it only grows at the end, so rsync --append works). If the database file is replaced (a restore, a compacted copy), the next step keeps the old archive as archive-<ms>.kdb and starts a new one.

Restore

Offline, into a new file; the server never overwrites:

kestro-server --restore DIR/archive.kdb --to restored.kdb --time 2026-11-17T14:32:10Z   # state then
kestro-server --restore DIR/archive.kdb --to restored.kdb --txid 48211                  # after that transaction
kestro-server --restore backups/app-20261117-140000.kdb --to restored.kdb               # a whole backup

--time takes ISO 8601 (UTC Z or +HH:MM) or unix milliseconds and picks the last archived point at or before it (precision: the archive interval); --txid cuts exactly after that transaction (stats().txid and every write’s version are transaction ids). Then start the server on the restored file. Embedded apps do the same in-process: Node db.archive(dir) / Database.restore(source, dest, {txid, time}), PHP $db->archive($dir) / Embedded::restore(...), Python db.archive(dir) / kestrodb.restore(...), C kestro_backup / kestro_archive / kestro_restore.

Reclaiming space (online compaction)

Updates and deletes leave old versions in the append-only log. compact() rewrites the file to hold only current values while reads and writes continue: current values go to a new file shard by shard (writers to a shard wait only while that shard is copied), transactions committed meanwhile are appended, and writes pause only for the last few transactions and the switch. The new file is checked in full (replayed) before it replaces the old one; a crash at any point leaves the database whole. Readers in other processes (readFrom) see STALE and reopen. It returns the committed bytes before and after.

  • Server (admin role): RemoteDB.compact(), PHP $db->compact(), Python db.compact().
  • Embedded: Database.compact(), Embedded::compact(), Local.compact(), C kestro_compact.
  • compactTo(path) still writes a compacted copy to a new file instead.

Replication

A follower is a second kestro-server holding a byte-identical copy of the leader’s log. It serves reads (SQL, key/value, in-process readFrom readers on its machine) and refuses writes with READONLY until it is promoted.

# on the leader: a user with the replica role (it may only replicate)
repl  replica  long-random-replica-token
# on the follower machine:
kestro-server --db /var/lib/app/replica.kdb --replica-of tls://leader.example.com:7820 \
             --replica-token-file replica-token.txt [--replica-ca ca.pem] --tcp 0.0.0.0:7820 --users users.txt
  • Seeding. A follower whose file does not exist yet copies the leader’s log first (online; the leader keeps serving), then streams.
  • Streaming. The follower asks for the groups after its own end, giving the hash of its last group; the leader answers at once or waits up to a second for the next commit, so changes arrive within milliseconds. The follower commits each transaction through its normal commit path: its log, hashes and chain come out byte-identical, and its key index, SQL tables, secondary indexes and column cache follow (catalog changes, such as CREATE INDEX or ALTER TABLE, included). Each transaction is durable on the follower before the next is requested.
  • Safety. A follower that no longer continues the leader’s log (the leader was compacted or restored) stops with STALE; a different chain after applying stops with DIVERGED. Delete the follower’s file and restart it to reseed. Network errors and leader restarts only cause a reconnect (with back-off).
  • Status. stats().replica on the follower: state (streaming, reconnecting, stopped, promoted), leaderTxid, lagTransactions, lastContactMs, lastError; and stats().readOnly.
  • Failover (manual). For plain --replica-of followers: stop writes to the old leader, wait until lagTransactions is 0 (or, with --sync-replicas, at once), then promote() the follower (admin; Node RemoteDB.promote(), PHP $db->promote(), Python db.promote()) and point clients at it. For automatic failover, run a cluster.
  • A follower’s file must stay identical: compaction and writes are refused on it; back it up and archive it like any other database.

Synchronous replication

By default a commit is acknowledged by the leader before followers have it, so a leader lost without warning can take its last transactions with it. Start the leader with --sync-replicas N and a write (an autocommit SQL write, a COMMIT, or a key/value write) is answered only once N followers have it durably: a leader that dies right after answering loses nothing (RPO 0).

  • A follower’s next replication request confirms everything before it, so this costs one network round trip per commit group (concurrent writers share it), not one per write.
  • If fewer than N followers confirm within --sync-timeout (5 s), the leader logs KESTRODB SYNC degraded and goes on alone (stats().sync.degraded) until a follower catches up (KESTRODB SYNC restored).
  • With --sync-strict it never goes on alone: writes wait for the followers however long it takes (availability traded for zero data loss).
  • stats().sync: followers, acknowledgedEnd, degraded, waits, timeouts.

Cluster: automatic failover

Three (or five) kestro-servers, each listing every member, elect one leader among themselves. The leader takes the writes; the others follow it and serve reads. When the leader fails, the others elect a new one within about two election timeouts (under a second with --election-timeout 400ms on a local network; 1.5 s is the default) and clients carry on.

# users.txt on every member: the cluster token has the replica role
admin    admin    long-random-admin-token
cluster  replica  long-random-cluster-token
# on each machine (the list is the same everywhere; --cluster-self names this machine):
kestro-server --db /var/lib/app/db.kdb --create --tcp 0.0.0.0:7820 --users users.txt \
  --cluster tcp://db1:7820,tcp://db2:7820,tcp://db3:7820 --cluster-self tcp://db1:7820 \
  --cluster-token-file cluster-token.txt
  • Clients are given every member: Node RemoteDB.connect('tcp://db1:7820,tcp://db2:7820,tcp://db3:7820', ...) (or an array), PHP new KestroDB\Client('tcp://db1:7820,tcp://db2:7820,tcp://db3:7820', ...), Python kestrodb.connect(['tcp://db1:7820', ...]). A member that follows answers a write with READONLY ... the leader is tcp://db2:7820 (nothing was applied); the client moves there and sends it again, also while an election is under way (up to failoverTimeout, 15 s). Reads are served by whichever member the client is connected to; a follower’s reads can trail the leader by its replication lag.
  • No acknowledged write is lost. A write is answered once a majority of the members (the leader included) has it on disk. A member votes only for a candidate whose log is at least as up to date as its own (by the term of its last transaction, then its length), so any later leader has every answered write. A write that cannot reach a majority within --sync-timeout (5 s), or whose leader steps down first, fails with UNAVAILABLE: its outcome is unknown (as after a lost connection), so check before retrying.
  • One leader. Terms and votes are flushed to <db>.cluster before a member answers. A leader that cannot hear from a majority for one election timeout steps down, so a leader cut off from the others stops taking writes. Elections start with a pre-vote, and members that hear from their leader refuse to vote, so a member that was cut off cannot depose a working leader when it returns.
  • Rejoining. A member that was away catches up from the leader. A former leader holding writes no majority confirmed (it was cut off while they were in flight) finds where its log and the leader’s part, cuts its log back to there (KESTRODB CLUSTER log cut back to transaction N), restarts in-process and follows. A member without its file (new, or a replaced disk) copies the leader’s log first: start it without --create, which is for forming a new cluster (every member starts with an empty log).
  • Status. stats().cluster: self, term, role (leader, follower, candidate), leader, members, majority, elections, lastLeaderContactMs; stats().sync.
  • Sizes. Three members survive the loss of one, five the loss of two. Two members survive neither one’s loss (a majority of two is two).
  • Compacting the leader makes each follower copy its log again (it no longer continues their copies): plan it for a quiet time. promote() is refused in a cluster.

The cluster token is the members’ secret. A client holding it could start elections. A cluster answers a write once a majority has it, so members far apart add their round trip to every write: KestroDB does not do clusters across regions.

Embedded PHP and Python

kestrodb.open() gives Python an embedded database owned by the process, like sqlite3, through the C library. PHP has the same with KestroDB\Embedded::open($path, $create) (in-process SQL through FFI).

import kestrodb

with kestrodb.open("app.kdb", create=True) as local:     # this process owns the file
    v = local.set("users", "kestro", {"name": "Kestro"})   # durable when it returns
    local.get("users", "kestro")
    local.set("users", "kestro", {"name": "H."}, expected_version=v)
    local.sql("SELECT * FROM users WHERE id = ?", [1])
    local.count()

It has the same methods as the server client (get/get_many/set/delete/batch/sql and the query helpers), plus count(), backup(), archive() and compact(), all in-process; kestrodb.restore(...) restores into a new file. In the Python benchmark, one embedded process wrote 9,200 durable writes/s, against 4,500/s through the server.

use KestroDB\Embedded;
$local = Embedded::open('/data/app.kdb', true);   // no server; needs ext-ffi and the C library

KestroDB\Embedded and ['readFrom' => ...] use PHP FFI and kestrodb.dll / libkestrodb.so (option library, the KESTRODB_LIBRARY environment variable, or ../../bin). Embedded also has backup, archive, compact and Embedded::restore(...).

The C API

One shared library (kestrodb.dll / libkestrodb.so / libkestrodb.dylib) that any language with a C foreign-function interface can load: PHP FFI, Python ctypes, Go cgo, Java FFM/JNA, C# P/Invoke, Rust, Ruby FFI, ... Other languages need a small binding over src/kestrodb.h.

Open modes

ModeUse
KESTRO_OPEN_READERReads in this process while another process writes (usually kestro-server). Any number of processes can do this at once; each read sees every write acknowledged before it started. Handles are shared per path within a process and stay open for the process lifetime, so opening again is free.
KESTRO_OPEN_OWNERThis process is the only writer (an embedded database, like SQLite in one process). Add KESTRO_OPEN_CREATE to create the file.

  • kestro_get returns 1 found, 0 missing, -1 error. *value points to a per-thread buffer valid until this thread’s next kestro_get on any handle.
  • kestro_get_many reads up to 4,096 keys from one committed state. Payload: u32 count, then per key u32 length + bytes. Reply (per-thread buffer): u8 0, u32 count, then per key u8 found [, u64 version, u32 length, value].
  • kestro_set, kestro_delete and kestro_batch work on owner handles only and are durable when they return. kestro_batch is all-or-nothing, in the server’s batch encoding.
  • kestro_sql runs one statement on an owner handle. params is a JSON array for the ? placeholders (NULL or "" for none); *result is {"rows":[...]} or {"changes":n,"lastInsertId":id} in a per-thread buffer. A transaction (BEGIN ... COMMIT) belongs to the handle that runs it.
  • kestro_compact is online compaction (before/after: committed bytes of the old file at the switch and of the new one). kestro_backup writes an online backup to a new file on an owner handle. kestro_archive appends what was committed since the last call to dir (archive.kdb + timeline). kestro_restore writes a new database at dest from source, cut after txid (0: all), or at the last archived point at or before at_ms (unix milliseconds; -1: unused).
  • Keys are bytes (1–1024). To share a database with the language clients, use their key form: collection + "\0" + key.
  • Every function that can fail takes err/errlen and writes a message that starts with an error kind (INPUT, CONFLICT, CORRUPT, STALE, LOCKED, IO, ...).
  • Reader handles are shared and cached; closing one ends it for this process.
