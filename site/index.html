KestroDB 0.9 · C++17 engine · one file

A durable database in one file, speaking the SQL you already know.

Like SQLite, KestroDB lives next to your app. Rows are JSON documents, every write is on disk before the call returns, and the same database serves Node.js, PHP, Python, Java, .NET, Rust, Go and any language with a C FFI — in-process, or through kestro-server with many connections at once.

Why KestroDB

Fast where apps feel it, honest where it isn’t.

An embedded engine built for durable writes and point reads, with the SQL and the clients you need to use it from a real application stack.

Durable writes, faster

Every write is on disk before the call returns. Concurrent writes share one flush (group commit). One-at-a-time durable writes measured 23,200/s against 6,600/s for LMDB on Windows, and durable single-row SQL INSERTs 5.4× SQLite; through kestro-server, durable single-row SQL INSERTs beat MariaDB 2.8× and PostgreSQL 1.05×.

SQL you already know

The common core of MySQL, PostgreSQL and SQLite: joins of every kind, correlated subqueries, window functions, CASE, UNION, enforced CHECK, foreign keys and UNIQUE, transactions with savepoints, upserts in all three dialects, secondary and unique indexes, and ?, $1 or :name parameters. Plus a key/value API for the fastest access by key.

One file

The whole database is a single file next to your app. Its format uses explicit little-endian integers and no OS-specific layout, so you can close it, copy it to another system and verify() it. Backups run online and verified, a continuous archive allows point-in-time restore, and compact() reclaims space while reads and writes continue.

Any language

An in-process Node.js addon, clients for PHP, Python, Node, Java, .NET, Rust and Go, and a C library (kestrodb.dll / libkestrodb.so) for Ruby, C/C++ and anything else with a C FFI. They all share the same keys, so they share one database.

Many connections, secured

kestro-server serves one database over TCP or a Unix socket, group-committing writes from every connection. At 4,000 connections it sustained 168,786 operations/s with 0 errors. Users get readonly, readwrite or admin roles and optional per-table limits, and TCP can be TLS-only (OpenSSL on Linux, Schannel on Windows). Followers replicate the log for reads, optionally synchronously, and a cluster of three or five servers elects a new leader on its own when one fails.

Integrity checks built in

Every transaction is stored with a SHA-256 hash chained to the previous one, and every value is checked against a checksum when read. Damaged data is reported as CORRUPT and never returned.

Where KestroDB does not lead

  • Row-returning scans: aggregates over a whole table read an in-memory column cache, but a SELECT that returns whole rows without an index reads and parses every row, because each row is a checksum-verified JSON document. Index the columns you filter on.
  • Against PostgreSQL over TCP (2026-11-19), single-connection durable INSERTs lead by only 1.05×. Opening a database measures 21.0M keys/s against 31.7M in 0.8.0: the first close after writes now flushes the commit slot once.
  • Reads through the server socket (one loopback round trip per read): 38,000/s with one PHP process, slower than in-process SQLite — which is why the clients read the file in-process when they can.
  • All of this is from one machine. Single runs on it move by 10–15% when other programs run, more than some Linux read margins (1.05–1.18×), and SQLite’s SQL numbers moved by about 10% between runs. Durable writes on Linux were measured under WSL2, whose virtual disk makes every flush slow for every engine. Run the benchmark on your own hardware before relying on it.

When not to use it

Know the limits before you pick it.

KestroDB has SQL tables with enforced column types and constraints, joins of every kind, correlated subqueries, window functions, transactions with savepoints, aggregates, secondary and unique indexes, backups, online compaction, replication and automatic failover. Today it does not have the following; the roadmap page has the full list.

  • The rest of SQL

    No deferred constraints, NATURAL joins, WITH before INSERT/UPDATE/DELETE, or full-text search.

  • Unindexed row scans

    A SELECT that returns whole rows without an index reads and parses every row; there is no column cache for row-returning scans.

  • Serializable concurrent writers

    Plain BEGIN transactions write one at a time; BEGIN CONCURRENT ones run side by side under snapshot isolation, which allows write skew. One process owns the file; others write through kestro-server.

  • Long production use

    It is fuzzed, power-loss tested in simulation, run under the address and thread sanitizers and soak-tested, but has not yet run real production workloads for long. No power-cut tests on real hardware or days-long soak runs yet.

  • Clusters across regions

    A cluster answers a write once a majority of its members has it, so members far apart add their round trip to every write.

  • Network or synced folders

    Network shares, cloud-sync folders and multi-host shared disks are not supported.
